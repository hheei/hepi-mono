# Build pi-proxy extension proxy package

## Goal

Create a new `pi-proxy` package that acts as a unified compatibility layer for Pi
extensions. The package should load or wrap other extensions through an `ExtensionAPI`
proxy, intercept their registrations, and let local adapters rewrite tools, commands,
events, flags, and context behavior without forking upstream packages.

The first useful integration is a `pi-fff` + `pi-hashline` adapter: run `pi-fff` in
override mode, wrap its registered `grep` tool, and rewrite grep output into the same
hashline anchor contract used by `pi-hashline` read/replace tools.

## Background

- Pi extensions are TypeScript modules that register tools, commands, flags, providers,
  and event handlers through `ExtensionAPI`.
- `pi-fff` can run in `override` mode, registering FFF-backed tools under built-in names
  like `grep` and `find`.
- `pi-hashline` exports `initHasher`, `lineHashes`, and `HASH_SEP` from
  `packages/pi-hashline/src/hashline/index.ts`.
- The hashline edit flow works best when `read`, `grep`, and `replace` share the same
  `HASH│content` contract and editing no longer relies on line numbers as primary
  anchors.
- The repository is a Bun workspace. New extension packages live under `packages/*`, use
  `type: "module"`, expose TypeScript source through `main`, and declare Pi entries in
  `package.json` under `pi.extensions`.

## Requirements

- Add a package named `@hheei/pi-proxy` under `packages/pi-proxy`.
- Provide a reusable `ExtensionAPI` proxy mechanism that can intercept at least:
  `registerTool`, `registerCommand`, `registerFlag`, `on`, and `getFlag`.
- Model proxy behavior as composable adapters so future cross-extension support does not
  require rewriting one monolithic proxy.
- Include an adapter that wraps `pi-fff` in `override` mode.
- The `pi-fff` adapter must wrap the registered `grep` tool and keep the public tool name
  as `grep`.
- Wrapped `grep` output must replace grep match/context line prefixes with hashline
  anchors in the form `HASH│content`, using `pi-hashline`'s actual hasher and separator.
- File headers and non-line notices from `pi-fff` should remain understandable in output.
- The adapter must avoid depending on private `pi-fff` closure state. It may wrap the
  registered tool and parse current text output unless structured match details become
  available later.
- The implementation should keep upstream packages updateable: no vendoring or direct
  modification of `packages/pi-fff` or `packages/pi-hashline` for the first version unless
  planning is explicitly revised.
- Tests should cover proxy interception and the grep-output hashline rewrite behavior.

## Acceptance Criteria

- [ ] `packages/pi-proxy/package.json` is a valid Bun workspace package manifest for a Pi
  extension package.
- [ ] `packages/pi-proxy/src/index.ts` exports a default Pi extension entry.
- [ ] A reusable proxy helper can rename, drop, or wrap tools registered by an upstream
  extension.
- [ ] A `pi-fff` adapter forces or simulates `fff-mode=override` for the wrapped
  extension.
- [ ] When `pi-fff` registers `grep`, `pi-proxy` registers a wrapped `grep` whose output
  lines use `HASH│content` anchors generated by `pi-hashline`.
- [ ] The hashline rewrite uses file contents from the active Pi cwd and preserves file
  grouping from grep output.
- [ ] The rewrite handles match lines and context lines from `pi-fff` grep output.
- [ ] Tests demonstrate hashline rewrite output for at least one file with a matched line
  and one context line.
- [ ] `bun run check` passes, or any narrower validation is documented with the reason.

## Out of Scope

- A full generic third-party extension loader with dynamic package resolution.
- Monkey-patching private ESM dependencies or upstream closure-local variables.
- Replacing `pi-hashline` read/replace behavior.
- Redesigning `pi-fff` internals or requiring upstream PRs for the first version.
- UI settings for adapter configuration unless needed to validate the MVP.

## Open Questions

- Should the first version expose only the composed `pi-fff` adapter as the default
  extension, or should it also export a public helper API intended for other local
  packages to import immediately?
